# M5 补充实验：云端大模型对照（10 个模型，按账号积分）

> 日期：2026-11-06　｜　模型：WorkBuddy 云服务 LLM（keyless，按账号积分计费）
> 数据：`reports/m5_cloud_compare.json`、汇总 `reports/m5_all_models.json`
> 判据与本地实验**完全相同**：30 条难工单 → 契约调用 → 特征去除体积 IoU；纠错用同一份错误起点

## 1 为什么还要接云端

本地那批 Q4 量化模型（`docs/M5-MODELS.md`）最好只到 IoU 0.842（H06 改题后重算），最差 0.462，
而且**失败全部集中在语言层**（方位词 0.229、相对深度 0.292）。

这留下一个无法回答的问题：**这是量化损失、规模限制，还是任务本身的天花板？**
本地全 Q4 量化，参数 8–15B，既不能升精度也不能换厂商。
云端模型提供了一个"能力上界"参照：如果云端旗舰也停在 0.8，说明是任务难；
如果云端打满，说明本地瓶颈是模型能力，与契约层无关。

## 2 接入方式（`LLMClient(api="cloud")`）

`src/cadcam/agents/llm.py` 新增第三个后端。与本地两个后端相比有四个硬约束：

| 约束 | 表现 | 处理 |
|---|---|---|
| **只支持流式** | 非流式直接拒 | 读 SSE 帧拼回整段文本 |
| **鉴权方式不同** | 不是 `Bearer`，是 `x-wb-webapp-access-key` + `Origin` 同源 | 显式带两个头 |
| **思考与答案分离** | `delta.reasoning_content` vs `delta.content` | 分开累计，只把 content 当答案 |
| **有配额与限流** | 429 带退避、`usage.quota` 可读 | 指数退避重试 |

配置不写死在源码里：

```bash
# .workbuddy/cloud.json（已 gitignore）或环境变量
export WBCLOUD_ENDPOINT="https://<app>.app.workbuddy.host"
export WBCLOUD_KEY="wbpk_..."
```

调用侧与本地完全一致，所以脚本不用改判据：

```python
from cadcam.agents.llm import LLMClient
c = LLMClient(base_url="", model="deepseek-v4-pro", api="cloud")
data, resp = c.complete_json(messages, schema, max_tokens=2400)
```

### 4.2 一道欠约束题，是怎么被找出来的（B13）

第一轮跑完，10 个云端模型的 IoU 停在 0.938–0.987，**没有一个满分**，而且都卡在同一条：

> H06（原表述）=「80×100×50：两个 40×20 深 6 的腔，关于 y=50 上下对称，x 都居中。」

问题在**只说了对称、没说距离**。逐题统计显示：**8/9 个云端模型给出别的合理读法**
（贴边并排、间距各 20 等），IoU 落在 0.0–0.6。这不是模型错，是题目欠约束。

**改法**（保留"对称"这一考点，只补足唯一解所需的信息）：

> H06（改后）=「……两个 40×20 深 6 的腔上下对称排列，x 都居中，
> **下腔下边缘距 y=0 留 10，两腔中间留 40 的空隙**。」

改完之后只补跑这一条（`scripts/m5_patch_orders.py --task H06`，15 个模型约 100 秒）：

| | 改题前 | 改题后 |
|---|---|---|
| 云端 10 个模型 | 1 个对（0.333–0.6 不等） | **10/10 全对（IoU = 1.0）** |
| 本地 5 个模型 | 全错 | 仍全错（0.0–0.6） |

这张表本身就是一条结论：**改清表述后云端全对、本地全错**——
说明第一轮的低分是题目问题，而本地模型的低分是**真的读不懂**这种复合表述
（"下边缘留 10、中间留 40"要连做两次位置推算）。

改题后 **6/10 个云端模型在 30 条上零误差**（deepseek-v4-pro、v4.1-flash、glm-5.3-flash、
hy4std、mimo-v2.6-pro、step-5-preview）。任务集对云端旗舰**依然饱和**——
但这个饱和是"题目太简单"，不再是"题目有歧义"，两者必须分开说。

### 4.3 合法率仍然全是 1.000 —— 契约层的价值不随模型变

15 个模型（5 本地 + 10 云端）、450 次调用，**合法率全部 1.000**（llama3.1 有一条例外，
是执行阶段失败不是契约违规）。也就是说：

- 模型能力决定"中文读得对不对"（IoU 0.462 → 1.000，跨 2 倍差距）；
- 契约层决定"能不能执行"（15/15 模型都是 1.000）。

这两件事**完全解耦**，正是本文把几何交给确定性代码的理由。

### 4.4 结构化反馈：价值随模型能力显现（这条修正了之前的结论）

纠错专项用同一份错误起点（型腔被放在正中，正确是左上角），三种反馈各 4 次：

| 模型档位 | vague（"不对，重做"） | structured（逐特征余料） | + 正确坐标 |
|---|---|---|---|
| 本地 8B（qwen3:8b） | 0/4 | 0/4 | 4/4 |
| 本地 14B（qwen3:14b） | 0/4 | 4/4 | 4/4 |
| **云端 mimo-v2.6-pro** | **1/4** | **4/4** | 4/4 |
| **云端 glm-5.3** | **2/4** | **4/4** | 4/4 |
| 云端其余 8 个 | 3–4/4 | 3–4/4 | 4/4 |

两种读法都成立，必须一起说：

1. **结构化反馈确实能带来增益**，但只在"模糊反馈本来会失败"的模型上可见
   （mimo 1→4、glm-5.3 2→4）。本地 8B 上三档全 0 或全 4，看不出差别。
2. **对强模型，模糊反馈也够用**（8/10 云端模型 vague 就 3–4/4）。
   即"给不给结构化错误"在强模型上**不再是瓶颈**——它自己能看懂"不对"。

所以正确的表述是：**结构化反馈的价值 = f(模型的指令跟随能力)**，
不是恒定的"有用"或"无用"。这也解释了为什么 M4 的确定性修复器在 8B 上照样有效：
它不依赖模型理解错误，而是把修法写死。

## 5 三个工程发现

1. **目录 enabled ≠ 可用**（§3 的 hunyuan-2.0-thinking）。
2. **思考模型的 token 预算会咬人**：glm-5.3 首次跑 H03 时 reasoning 写了 9 040 字，
   把 2 400 的预算吃光、`content` 返回空；提到 8 000 后才拿到输出。
   对 `onlyReasoning: true` 的模型，`max_tokens` 要按"思考 + 答案"一起估。
3. **两套鉴权不能混**：本地走 `Bearer`/无鉴权，云端走 `x-wb-webapp-access-key` + `Origin`；
   把云端 endpoint 塞进 OpenAI 客户端会因为缺 Origin 报 `auth_origin_mismatch`。

## 6 对论文的影响

**加强的部分**

- 跨模型表从 5 个扩到 **15 个**（5 本地量化 + 10 云端），且判据、提示、错误起点完全一致；
- "能力边界由动作空间决定"有了更强证据：同一批云端模型，自由写 G-code 是 0/10（§5.6 的 B7），
  走契约是 30/30、IoU 0.938–1.000；
- 契约层价值与模型能力**解耦**（合法率恒 1.000，IoU 跨 2 倍）。

**必须写进限制的部分**

- **30 条任务集对云端已饱和**（改题后 6/10 打满 1.0000、其余 0.962–0.971），
  无法用这批题区分云端旗舰；要比较旗舰需要更难的任务集，见 `docs/M5-HARD2.md`（20 条新题）；
- 云端模型的参数量不公开，**不能把差距归因到规模**，也不能与本地 Q4 的差距
  简单归因到"量化损失"——这三个因素（规模、厂商、量化）在本实验里是混淆的；
- 单次运行（`temperature=0` 仍有方差），未做多次重复；
- 积分消耗只能读网关返回的 `quota.percent`，其语义（已用/剩余）未在文档中定义，**不主张精确成本**。

## 7 复现

```bash
# 1) 一次性：在 WorkBuddy 里给项目开云服务，把 endpoint/publishableKey 写进
#    .workbuddy/cloud.json（已 gitignore），或设 WBCLOUD_ENDPOINT / WBCLOUD_KEY

# 2) 单模型全量（30 工单 + 12 次纠错，约 2–6 分钟）
PYTHONPATH=src python scripts/m5_model_compare.py --provider cloud \
    --models deepseek-v4-pro --repeats 4 --max-tokens 2400 \
    --out reports/m5_cloud_compare.json

# 3) 只改某道题的表述后，补跑这一条并回收（不重跑整个任务集）
PYTHONPATH=src python scripts/m5_patch_orders.py --task H06

# 4) 合并本地 + 云端成一张表
PYTHONPATH=src python scripts/m5_cloud_report.py
```

不开云服务也能验证接入是否正确：`pytest tests/test_agents.py`（云端分支用假客户端覆盖）。

## 8 与本地实验的关系

| | 本地（`docs/M5-MODELS.md`） | 云端（本文） |
|---|---|---|
| 成本 | 零边际成本，4090 本地 | 账号积分，约 218 k token |
| 隐私 | 图纸不出机器 | 工单文本出网 |
| 最强 | qwen3:14b，IoU 0.842 | 6 个模型并列 **1.000（30/30）** |
| 短板 | 方位词（0.229）、相对深度（0.292） | 只剩题目歧义（H06） |
| 适用 | 日常迭代、离线车间 | 一次性高价值任务、无 GPU 环境 |

一句话：**本地模型的瓶颈是语言，云端模型解决语言但暴露出题目本身的天花板。**
两者都不能替代验证器——15 个模型的合法率都是 1.000，但没有一个能保证"意图正确"（H06）。
